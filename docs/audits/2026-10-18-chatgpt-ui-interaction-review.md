# Socrates 对照 ChatGPT：UI 与交互审查

日期：2026-10-18。范围：当前工作区，包含已有、尚未提交的持久化研究任务改动。本轮仅新增审查文档，不修改产品代码。

## 判断与证据边界

Socrates 已有较完整的聊天界面基础。当前最值得优化的是入口含义、功能发现、任务反馈、结果迭代和跨端一致性。继续调整几像素的圆角或灰阶，优先级低于让用户理解“点击后会发生什么”。

证据分为三类：

- **本轮实测**：本地生产构建；Chromium；模拟登录/API；桌面 1440×900、手机 390×844；中英文切换相关代码检查；浅深色截图与按钮代理探针。
- **代码确认**：当前源码可以证明的能力与限制。Universal App 本轮只检查源码，没有启动原生客户端。
- **设计建议**：根据上述观察提出的方案，尚未通过真实用户行为数据或 A/B 实验验证。

本轮没有登录 ChatGPT 在线产品进行同条件操作或性能测量。初次审查的 ChatGPT 功能依据检索并打开的官方资料；像素参考来自仓库 `docs/ref/chatgpt-parity.md`（2026-09-28、未登录桌面）与 `docs/ref/mobile-reference-2026-10-04.md`。随后用户提供了四张手机网页截图，作为本次补充的直接视觉依据，见下一节。这些截图不能代表所有账户、套餐或灰度界面。官方资料中的 Web、桌面版、Work 与 Codex 能力分别标注，不能混用。

由此修正初次建议：

1. **双语音按钮本身符合参考。** 问题是 Socrates 两个入口调用同一听写路径。目标可保留麦克风＝听写、波形＝连续语音；若连续语音暂未实现，短期去重只能作为过渡方案。
2. **默认手机首页保持简洁。** 本图没有常驻起步卡，不能把“留白多”直接判作体验缺陷。辅导引导调整为按需/首次进入的产品实验，不属于像素对齐必做项。
3. **参考并不要求缩减主导航。** 图中同样保留多个一级入口，应先对齐分组、顺序、快捷动作和可用性，再依据使用数据决定收敛。
4. **推理强度标签并非缺失功能。** 现有实现已支持非默认强度标签；截图的“高”不能证明参考默认显示强度，也不能从灰色外观判断按钮禁用。
5. **颜色与图标按职责判断。** 蓝色波形可作为明确语音状态的参考，但不单独增加一套配色。右上角图标在截图中没有文字标签，不能只凭形状断定点击功能。

尺寸比较需排除浏览器地址栏和系统状态栏。以 390px 宽归一化作粗估，网页区域约 769px 高，侧栏约占屏宽 65%，即约 254px；这是截图换算，并非读取 DOM 得到的 CSS 值。当前 `tokens.css` 的手机侧栏变量为 `min(330px, 80vw)`，在 390px 下对应 312px，`mobile-sidebar.css` 将导航行设为 48px，与旧参考文档的 254px/40px 也存在漂移。需在相同视口、展开状态和实际级联下重新测量后再改，不能直接使用 1200px 图片尺寸作为网页像素。

新的移动端优先顺序：居中模式入口 → “最近”整理行为 → 侧栏顺序/项目＋与几何核对 → 账户菜单精修。语音连续会话单独按能力建设。头像、姓名、聊天标题继续使用实际账户数据，品牌保持 Socrates。

截图无法确认键盘焦点、ARIA、菜单点击后结果、语音会话质量、动效或软键盘避让；截图内较淡的文字/图标需要进一步测量对比度。此补充只更新审查判断，未更改原有移动参考契约、产品代码或测试基线。

## 第一批：直接影响理解与发现

### 1. 区分听写与连续语音（P1，实测＋代码确认）

空输入时，输入框右侧同时出现麦克风和波形按钮。代理 `window.toggleSpeechInput` 后依次点击两者，在桌面/手机、浅深色四组均记录到 `['topic', 'topic']`：两者调用同一语音路径。`src/ui/voiceInput.js` 使用浏览器 SpeechRecognition，最终把识别文本填入输入框。

因此目前两个视觉入口没有对应两个清楚不同的任务。波形容易形成“进入连续语音会话”的预期。本轮没有实录音或测量识别质量；代理仅验证点击路由。

用户随后提供的图 1 证实 ChatGPT 网页也保留麦克风与波形双入口。对齐目标应是麦克风负责听写、波形进入真实连续语音；主按钮在有草稿时发送、生成时停止。连续语音能力尚未提供时，可临时收敛入口，但不能把删除波形称为对齐该截图。可用性随浏览器变化时，提前显示原因和替代入口。

实现位置：`src/ui/legacyShellListeners.js`、`src/ui/topicSetup.js`、`src/react/lib/boot/indicatorComponents.tsx`。`index.html` 中“主按钮仅提交”的旧注释与当前行为不一致，应在实现调整时一并整理。

验收：每个按钮的名称、图标、点击行为一致；空/有草稿/生成/录音/不支持六种状态均可解释；无两个同名同功能语音控件。

### 2. 收敛“＋”菜单，并前置搜索（P1，实测）

桌面菜单可滚动区域高约 461px，内容高 579px；手机约 358px，内容高 900px，滚到底需移动 542px。手机首次展开仅能看到相机、照片、上传、图像、网页搜索与深度探索；深度研究排在下一项。搜索框在末尾。

滚动探针确认尾部搜索可到达，**不是菜单内容不可访问**。问题是长列表缺少明显的功能总览，用户需先滚动才能使用搜索。网页搜索、深度探索、深度研究的可见标签接近；现有描述虽用于 aria-label，普通视觉下被 CSS 隐藏。

建议：固定顶部搜索；首层展示上传、网页搜索、深度研究与常用动作，其余进“更多工具”；将相机/照片做紧凑资料入口。保留探索时，应说明其具体产物与研究的区别，如“探索一个主题”与“生成带来源的报告”。先通过名称/选中态/简短提示区分，不把所有说明常驻展开。

实现位置：`src/react/composer/composerToolsMenuData.ts`、`ComposerToolMenuItems.tsx`、`ComposerToolItems.tsx`、`src/ui/composerTools.js`。样式按现有 owner 约束修改，避免向 restore 层继续堆覆盖。

验收：手机首屏可发现主要任务；列表滚动时搜索可见；键盘可搜索、选择、Escape 返回触发器；选择后标签及占位文字明确。

### 3. 让手机辅导模式有按需起步路径（P2，产品实验）

手机首页当前主要为问候、留白和输入框；桌面的快捷操作与 tutor 三张起步卡没有等价的手机起步入口。`polish/home.css` 的 tutor starters 只在 `min-width:769px` 开放，`polish/mobile-shell.css` 隐藏普通快捷行。

这符合现有极简参考，用户补充的图 1 进一步支持保持默认留白。新用户是否因此难以发现学习能力需真实测试，不直接视为缺陷。可在**辅导模式首次进入或主动寻求帮助时**提供可关闭的轻量选择：“理解概念 / 给我练习 / 制定复习计划”；填写目标和现有水平后进入原有对话。老用户可显示“继续上次学习”。

这是产品实验建议；移动端已有 reference-pinned 契约，落地时应同步更新对应参考与视觉测试，保留独立控件密度及键盘安全区，不能直接把桌面三列卡挤进手机。

验收：从辅导首页一步填入可编辑的真实提示；不自动发送；新手可撤销；真实键盘打开后输入区不被遮挡。

### 4. 修正 Universal App 的无响应入口（P1，代码确认）

`apps/socrates/src/appNavigation.ts` 中 Scheduled、Plugins、Sites 仍使用 `onPress: () => undefined`。它们显示为正常导航，却没有反馈；这比视觉差异更影响用户信任。

建议按能力决定是否展示，或提供清楚的不可用说明与已支持的下一步。用共享能力表驱动入口与路由，防止 SPA、Universal Web、Android 各自维护一份“看似可用”的功能菜单。

验收：所有可见入口都能到达有效页面或产生明确反馈；Web 与 Android 各自检查返回行为。此项不能仅靠旧 SPA 的 Playwright 通过来验收。

## 第二批：把任务与结果串成连续体验

### 5. 研究任务增加活动入口和完成反馈（P2，代码确认）

当前 `ResearchJobs.tsx` 已处理排队、运行、重连、取消、失败/重试，成功后由报告消息承接。下一步应让用户离开该会话后仍可找到任务：侧栏活动入口、会话运行/未读标记、完成结果直达、失败原因和重试。

可增加研究计划/来源范围的可检查视图，但先判断是否需要额外确认步骤，避免每次研究都多一道门槛。暂停/恢复与运行中修改范围，需要相应后端语义，不能只画按钮。真实完成通知仍在现有交接文档的待办中；本轮没有证明生产关闭页面五分钟及进程重启的完整链路。

参考官方 Long-running work、Notifications、Web search。验收应覆盖切换会话、刷新、重复完成事件、失败返回和通知跳转，而不仅检查动画。

### 6. 让产物支持“继续改”，减少跳转（P2，代码确认）

`src/ui/artifactPreview.js` 已有图片/HTML 详情预览；其他 MIME 在该通用预览入口显示新标签页兜底。不能据此断言全项目不存在 PDF 或专用编辑器，但当前通用入口尚未形成统一文件审阅流程。

建议建立产物卡 → 预览 → 选段/选区反馈 → 修订结果 → 保存/下载/回到聊天的流程。桌面利用已有详情面板，手机进入全屏详情并保留返回点。优先支持 Markdown/代码及已有图片，再评估更重的文档批注和版本对比。

参考官方 Work with files 和 Image generation；桌面批注与 Canvas 的具体模式不应被当作所有 Web 账户已有的同款能力。

验收：继续编辑携带正确产物身份；返回保留聊天与草稿；失败保留上个结果；版本与下载对象一致。

### 7. 模型与推理配置面向任务表达（P2，截图观察＋设计建议）

当前桌面顶部显示 “Socrates Beagle”，弹层提供模型、思考强度、速度和管理模型，已实现渐进配置。建议继续保留专业设置，在其上提供简短用途或能力说明；只对真实支持的模型展示推理和速度选项，并保持更换模型时草稿/附件不丢失。

不要为了贴近 ChatGPT 将所有第三方模型硬套成同一套模式。先统一顶部名称、手机配置、工具菜单“更深入思考”和当前选中标签的语义；没有用户数据前，不必再加一个常驻模式切换器。

验收：用户能知道本轮将使用什么能力；不支持的选项有解释；桌面/手机配置表示同一状态。

### 8. 重生成、编辑与分支保留清楚的回退路径（P2，代码确认）

`src/chat/editBranch.js` 已支持消息编辑、重生成和克隆分支。当前消息工具栏没有同一位置的回答变体选择器。建议先在重生成前后保留用户可理解的旧回答恢复路径，再考虑消息级 `1/2` 切换；新会话分支应显示来源和返回原会话入口。

此项是本项目的可逆操作建议；本轮未登录 ChatGPT 验证当前 Web 变体控件，不以官方 Codex 的 fork 文档证明 Web 像素行为。

验收：重生成失败可恢复旧答案；编辑影响后续消息前有清楚预期；切换版本时引用、附件和工具结果属于对应版本。涉及数据模型，独立迭代。

### 9. 让上下文与记忆可理解（P2，代码确认＋设计建议）

项目目录与记忆管理已经存在，记忆列表当前主要显示 key/value 与删除。建议在会话配置中说明项目、使用的资料和个性化作用域；为记忆补充可用的来源与编辑/禁用入口。只有服务端实际记录并提供了“本轮使用的记忆”，才展示相应标记，不能从客户端配置推断使用事实。

参考官方 Projects 和 Personalize。验收围绕切换项目、关闭记忆和临时聊天的真实语义，避免只换名称或图标。

### 10. 长会话先建立体验预算（P2，代码确认，性能收益待测）

`progressiveMount.ts` / `useProgressiveMessageMount.ts` 采用先挂 12 条再补齐的策略，当前仍不是有界虚拟列表。历史审计的 240 条/7,560 节点属于旧测量，本轮不冒充新的 profiling。

建议固定 200/500/1000 条混合内容负载，记录输入响应、滚动帧时间、长任务、节点与内存；据此决定窗口化或按回合回收。必须同时保护会话内查找、复制、文本选择、屏幕阅读器、返回历史锚点与 live 回合。不要用“像 ChatGPT”作为重写稳定滚动链路的理由。

## 优先级与落地顺序
